`qitos.kit` provides concrete, reusable building blocks for common agent authoring patterns. Components compose the `Agent` façade and the minimal agent loop; they do not introduce a second orchestrator.

Key terms used on this page:

- **tool set**: a bundle of related tools with shared lifecycle hooks
- **environment**: a provider-neutral runtime backend for file, shell, GUI, or web operations
- **journal**: the durable per-run record of model, Tool, and lifecycle transactions
- **harness**: the wiring layer that resolves a model family into a transport with context and tool policies
- **preset**: a reusable configuration bundle for a model family
- **trace**: a structured log of all run events and steps

```python
from qitos.kit import WindowMemory, CodingToolSet, HostEnv, ...
```

## How to read this page

Use this page as a capability map for QitOS authoring.

| If you are deciding... | Start here |
|---|---|
| How to keep useful context in long runs | Memory |
| Which tools to expose | Tool sets |
| Which ready-made registries to start from | Preset builders |
| How to start screenshot-first multimodal work | `ScreenshotEnv` and the visual guide |
| How to build desktop / computer-use agents | `DesktopEnv`, `ComputerUseToolSet`, and the desktop guide |

## Capability map

### Tool presets

- `coding_tools(...)` for the canonical coding workspace
- `computer_use_tools()` for provider-neutral desktop / GUI action workflows
- `advanced_coding_tools(...)` for a Claude-style coding preset
- `web_tools()` for web research and extraction
- `task_tools(...)` for persistent task-board workflows
- `SkillToolSet(...)` for read-only bundled Skill disclosure
- explicit `qitos.kit.tool.experimental.security_research` imports for security research workflows
- `thinking_tools()` for explicit thought-recording flows
- `notebook_tools(...)`, `report_tools(...)`, and `epub_tools(...)` for narrower scenarios

### Environments

- `ScreenshotEnv` for screenshot-first multimodal and GUI-adjacent workflows
- `DesktopEnv` for OSWorld-inspired desktop and computer-use loops
- `TextWebEnv` for text-browser-style web observation
- `TmuxEnv` for interactive terminal workflows

`ScreenshotEnv` is the first built-in multimodal environment. Use it when you want to test screenshot-based reasoning, visual-web prompting, or the new qita visual-asset path without committing to a full benchmark adapter.

`DesktopEnv` builds on the same multimodal core but adds an OSWorld-style desktop lane: screenshot + accessibility + terminal observation, GUI controller ops, and container-first provider boundaries.

### Long-running context blocks

- `WindowMemory`, `SummaryMemory`, `VectorMemory`, and `MarkdownFileMemory` for cross-step recall

### Planning

- `UpdatePlanTool` / `update_plan` commits a complete dependency-aware Plan to the
  current Session journal. Nodes have stable ids, dependencies, explicit durable
  states, and optional Child owners. Readiness is derived from completed dependencies.
  An empty Plan has no TODO projection; a Plan without dependencies or owners renders
  as a plain TODO list.

Child ownership is not model-authored. Pass a ready node id as the Agent Tool's
`plan_assignment`; the Child supervisor commits the generated handle to the Plan before
it writes `child.started`.

<Accordion title="WindowMemory">

Keeps the last N records in memory. Oldest records are dropped when the window overflows.

```python
from qitos.kit import WindowMemory
```

**Constructor**

```python
def __init__(self, window_size: int = 20)
```

|-----------|---------|-------------|
| `window_size` | `20` | Maximum number of records to retain in memory |

**Usage**

```python
from qitos.kit import WindowMemory

memory = WindowMemory(window_size=30)
agent = MyAgent(memory=memory, ...)
```

</Accordion>

| Parameter | Default | Description |

<AccordionGroup>

<Accordion title="CodingToolSet">

Full coding bundle combining editor, codebase search, file I/O, shell, and optionally notebook tools.

```python
from qitos.kit import CodingToolSet
```

**Constructor**

```python
def __init__(
    self,
    workspace_root: str = ".",
    shell_timeout: int = 30,
    include_notebook: bool = True,
    *,
    enable_lsp: bool = True,
    enable_tasks: bool = True,
    enable_web: bool = True,
    profile: str = "full",
    include_http_tools: bool = False,
    auto_approve: bool = False,
    allow_local_fallback: bool = True,
    process_env: Mapping[str, str] | None = None,
)
```

Profiles expose one exact lowercase tool surface. `glob` and `grep` use fixed-argv
`rg`, respect ignore files by default, and accept separate `include_hidden` and
`include_ignored` controls.

`run_command` executes a command after the normal tool-admission boundary. It does not
repeat permission classification inside the handler or expose model-controlled
`read_only` and `allow_destructive` switches. Applications that need command policy
apply it through the executor before invoking the tool. The `shell` and `full` profiles
also expose `process_list`, `process_read`, `process_write`, `process_wait`, and
`process_terminate`. These tools share one environment capability, bind opaque ids to
the active Run, preserve full logs outside the bounded model view, and respect the
current absolute Tool deadline.

`process_env` optionally supplies one complete application-owned environment snapshot
for local shell, fixed-argv, and background subprocesses. Leave it unset to preserve
normal inherited-environment behavior.

**Typical usage**

```python
from qitos import ToolRegistry
from qitos.kit import CodingToolSet

registry = ToolRegistry()
registry.register_toolset(
    CodingToolSet(
        workspace_root="/path/to/project",
        include_notebook=False,
        enable_lsp=False,
        enable_tasks=False,
        enable_web=False,
    )
)
```

</Accordion>

<Accordion title="SkillToolSet">

Expose a bounded catalog from application-owned, read-only Skill roots, load one
selected `SKILL.md` without truncating its content, and page its linked UTF-8
resources. Installation and package discovery are deployment concerns and are not
available to the Agent through this toolset.

```python
from qitos import ToolRegistry
from qitos.kit.tool.skill import SkillToolSet

skills = SkillToolSet(bundled_roots=["/opt/my-agent/skills"])

# Applications that only allow bundled assets register exactly these three tools.
registry = ToolRegistry()
registry.register(skills.list_skills)
registry.register(skills.load_skill)
registry.register(skills.read_skill_resource)
```

Roots are scanned during construction and when `refresh_bundled_skills()` is called.
Discovery recurses until it reaches a directory containing `SKILL.md`, then treats that
directory as one Skill and does not reinterpret nested files as another Skill. Earlier
configured roots win name collisions. Missing roots, invalid manifests, unreadable or
escaping resources, and shadowed names become typed `BundledSkillDiagnostic` values;
valid siblings remain available and refresh atomically replaces the old catalog.

`list_skills` returns stable name-sorted summaries, availability, bounded diagnostics,
and a bounded entry limit. `load_skill` requires one exact catalog name and returns the
complete validated snapshot, declared requirements, stable relative resource
identifiers, and both instruction-only and whole-bundle SHA-256 revisions. Pass an
immutable `available_requirements` collection when constructing the toolset to gate
full loading before instructions reach the model. Requirement identifiers are opaque
to QitOS, so an application can use exact values such as `command:nmap` and
`tool:run_command`. Omitting the collection preserves compatibility but reports
availability as `unchecked`.

`read_skill_resource` accepts only an identifier captured by the latest refresh,
rechecks the resolved path against the selected Skill root, verifies that its bytes
still match the bundle revision, and returns an opaque content-bound cursor when a
UTF-8 resource needs another page. Applications can use
`bundled_skill_snapshots()` and `bundled_skill_diagnostics()` to persist and revalidate
loaded instructions or explain discovery gaps. These paths do not invoke a provider,
install a package, or create a workspace registry.

<Accordion title="AgentTool">

Launch a fresh child-agent run from a normal tool call. Children run on the same
minimal-loop `Agent` as the parent; `qitos.kit.child.build_agent_child_invocation_factory`
wires one child run per invocation with narrowed tools, budgets and its own journal.

```python
from qitos.core import TaskBudget
from qitos.kit.child import build_agent_child_invocation_factory
from qitos.kit.tool.agent import AgentTool, ChildControlToolSet

tool = AgentTool(
    invocation_factory=build_agent_child_invocation_factory(
        model=model,
        tool_registry=registry,
        journal_directory=journal_root / "children",
    ),
    execution_scope=acquire_run_scoped_slot,
    execution_mode="background",
    max_delegate_depth=1,
    child_budget=TaskBudget(max_steps=200),
    child_allowed_tool_groups=("filesystem.read", "network"),
)
registry.register(tool)
registry.register_toolset(ChildControlToolSet(tool.supervisor), namespace="")
```

The model-facing arguments are `description`, `prompt`, optional `name`, and optional
`subagent_type`. The supervisor awaits the invocation factory, so construction can
acquire run-scoped resources without blocking the event loop. Each factory call must
resolve to an independent Agent; sharing a mutable history or model client between
concurrent children is unsupported.
`execution_scope` can enforce an application-owned concurrency or lifecycle boundary.
The result payload reports output, steps, elapsed time, stop reason, run id and the
`usage_complete` / `cost_complete` completeness flags; a terminal child's token and
cost accounting rides the typed `ToolResult.usage` carrier instead of the payload.
`child_budget` is an immutable `TaskBudget` and defaults to 200 steps. Invocation
factories receive it on `ChildLaunchRequest.budget`, together with the task, profile,
allowed tool groups, and working-directory fields needed by a product composition. The
built-in factory accepts only `profile="default"` and `working_directory=None`; it
rejects any other profile or working-directory request before model construction.
Products that resolve those policies must do so in their own invocation factory.
The built-in factory also carries the frozen parent Tool permission/scope policy into
the Child. A configured Child Env with a different policy is rejected because equality
alone is the only narrowing relation this generic factory can prove.
The async factory returns a `ChildInvocation`; live Agent objects never enter persisted child
requests or results. If the invocation creates a model client, trace, or other live
resource, set its async `cleanup` callback. The supervisor awaits cleanup after success,
failure, or cancellation before publishing the terminal result. If construction itself
fails or is cancelled before returning a `ChildInvocation`, the factory still owns and
must close every partially created resource before propagating the error.

`execution_mode` accepts `"foreground"`, `"optional_background"`, or `"background"`.
The optional mode exposes `run_in_background` to the model. The background mode omits
that argument, always returns a running receipt with a parent-scoped `ChildHandle`, and
attempts an `agent.child.completed` `RuntimeInput` to the exact parent run when a
parent mailbox callback is available. `AgentTool` retains an explicitly supplied
parent-history or snapshot value at launch; the minimal façade does not implicitly copy
its full transcript into every Child. It then delegates lifecycle ownership to a
Run-scoped `ChildSupervisor`. The supervisor does not call the invocation factory until
`execution_scope` admits the task. Queued work therefore retains
its launch context without allocating a model, Agent, or trace before it can run. If a
child has no final answer, the completion payload contains a bounded projection of its
recent tool evidence instead of silently dropping useful work.

The parent runtime supplies the async callback through
`ChildLaunchContext.post_runtime_event` and owns durable mailbox acceptance. Child
supervision stores its terminal result before awaiting that callback.
It also appends `child.started` before constructing the child Agent and
`child.terminal` before delivery. Resume rebuilds a started child from its own loop
journal when that journal holds a durable run terminal record, and otherwise closes it
as `interrupted` without replaying the Agent. Fork recovery ignores inherited
parent lifecycle records, so a fork cannot query or interrupt the parent's live Child.
If mailbox acceptance fails after `child.terminal`, the terminal result remains
queryable through the control tools. Re-projecting unconsumed background completion
inputs is owned by `qitos.kit.session.SessionHarness`: it re-projects them exactly
once from the recovered journal's own records while inherited fork facts are never
redelivered. Foreground results are
returned only through the original Agent ToolResult.

`active_background_count`, `child_result(handle)`, `wait_child(handle)`,
`interrupt_child(handle)`, `cancel_child(handle)`,
`snapshot_background_events()`, and `aclose()` expose lifecycle control to the owning
application. `ChildResult` uses one stable status vocabulary for running, completion,
blocking, budget exhaustion, failure, cancellation, interruption, and unknown handles.
Tool payloads keep that value in `child_status`; their top-level `status` remains the
canonical Tool execution status (`success`, `partial`, `running`, `error`, or
`cancelled`).
A snapshot projects only the active children's bounded, completed tool
results into `agent.child.snapshot` runtime events; it does not expose model responses or
reasoning. This lets an owner preserve evidence immediately before a forced conclusion.
`aclose()` cooperatively cancels outstanding child Agents; applications with run-scoped
resources should call it before those resources leave scope. It returns the number of
tasks still winding down after the requested bounded wait, and a later call can wait
again after an earlier non-blocking cancellation request. Background children and parent
completion delivery remain supervisor-owned asyncio tasks until both paths settle.
Terminal result state is stored before QitOS attempts to wake the parent. An
`execution_scope` that waits for an application slot should observe the
typed `ChildRuntimeContext.cancellation_requested` callback so teardown can wake a
child that has not entered its Agent yet.

`ChildControlToolSet` exposes exact `child_status`, `child_wait`, `child_message`, and
`child_interrupt` tools over that same supervisor. Wait timeout never cancels the Child.
Message acceptance is journaled when the child keeps a journal, and the message enters
the child run's steering queue, becoming visible at a
turn safe point. Unknown or foreign handles return stable `unknown` state. A terminal
Child rejects messages explicitly; continuing a terminal Session requires a product
resume factory rather than silently creating a different Child.

Delegation depth is checked before the factory runs. Multiple Agent calls execute in
parallel only when the parent's Tool execution policy allows `Agent` and the
tool remains marked concurrency-safe. The model-facing tool description recommends one
same-response call per independent multi-step task, while dependent steps stay in the
parent and cheap mechanical variants use ordinary tools in a bounded batch. The parent
should not repeat work it has already delegated.

```python
def __init__(
    self,
    headers: Optional[Dict[str, str]] = None,
```


`HTTPRequest.execute(args, runtime_context)` accepts an `args` dictionary containing
`method`, `url`, `params`, `data`, `json_data`, `headers`, `timeout`, `verify_tls`,
`allow_redirects`, and `max_content_chars`.

specific HTTP operation, pass an explicit QitOS `RetryPolicy`; otherwise the request
runs once.

<Accordion title="OpenAICompatibleModel">

Works with any OpenAI-compatible API endpoint — including SiliconFlow, Azure OpenAI, Tongyi, Zhipu AI, LM Studio, vLLM, and LocalAI.

```python
from qitos.models import OpenAICompatibleModel
```

**Constructor**

```python
def __init__(
    self,
    model: str = "default",
    api_key: Optional[str] = None,
    base_url: Optional[str] = None,
    system_prompt: Optional[str] = None,
    temperature: float = 0.7,
    max_tokens: int = 2048,
    timeout: int = 60,
)
```

| Parameter | Default | Description |
|-----------|---------|-------------|
| `model` | `"default"` | Model name sent to the API |
| `api_key` | `None` | Falls back to `OPENAI_API_KEY`; uses `"dummy-key"` if absent |
| `base_url` | `None` | Falls back to `OPENAI_BASE_URL`; **required** |
| `system_prompt` | `None` | Prepended as a system message to every call |
| `temperature` | `0.7` | Sampling temperature |
| `max_tokens` | `2048` | Maximum tokens in the response |
| `timeout` | `60` | Request timeout in seconds |

**Usage**

```python
from qitos.models import OpenAICompatibleModel

llm = OpenAICompatibleModel(
    model="Qwen/Qwen3-8B",
    base_url="https://api.siliconflow.cn/v1/",
    temperature=0.2,
)
agent = MyAgent(llm=llm, ...)
```
