title: "Tools and Registry"
description: "QitOS tools are plain Python callables marked with the @tool decorator. ToolRegistry collects them and makes them available to the agent loop for execution."
---

Tools are the actions your agent can take. At runtime, the agent loop uses `ToolRegistry`
for exact-name lookup, then the Tool executor validates, authorizes, and executes the
resolved tool.

## The `@tool` decorator

Mark any callable as a QitOS tool with `@tool`. The decorator attaches metadata to the function without changing its behavior — you can still call the function normally in tests.

```python
from qitos import tool
from qitos.core.tool import ToolPermission

@tool(
    name="read_file",
    description="Read the contents of a file at the given path.",
    timeout_s=10.0,
    permissions=ToolPermission(filesystem_read=True),
)
def read_file(path: str) -> str:
    with open(path, "r") as f:
        return f.read()
```

### `@tool` parameters

| Parameter     | Type                        | Description                                                                  |
| ------------- | --------------------------- | ---------------------------------------------------------------------------- |
| `name`        | `str \| None`               | Tool name used in model `ToolCall`s. Defaults to the function's `__name__`. |
| `description` | `str \| None`               | Description shown to the LLM. Falls back to the function's docstring.        |
| `group`       | `str`                        | Application-defined exposure group. Defaults to `"default"`.                |
| `timeout_s`   | `float \| None`             | Whole-action timeout, including admission, retries, and invocation.          |
| `retry_policy`| `RetryPolicy \| None`       | Explicit invocation retry policy. No policy means exactly one attempt.       |
| `permissions` | `ToolPermission \| None`    | Declares which system capabilities this tool requires.                        |
| `required_ops`| `list[str] \| None`         | Low-level operation identifiers required from the environment.               |

The Tool executor is the only tool retry owner. Validation, permission checks, and
approval run once; only the admitted invocation may repeat. All attempts and backoff
share the tool timeout and the run's earlier runtime deadline. Provider or HTTP
client retries must remain disabled when an explicit `RetryPolicy` is attached.

### `ToolPermission`

`ToolPermission` declares what the tool is allowed to do. The executor uses this information during preflight validation to check environment capabilities.

```python
from qitos.core.tool import ToolPermission

# A tool that reads files and makes network requests
ToolPermission(
    filesystem_read=True,
    filesystem_write=False,
    network=True,
    command=False,
)
```

All four fields default to `False`.

## ToolRegistry

`ToolRegistry` is the collection the agent loop queries when dispatching Tool calls. Pass it to the `Agent` constructor.

```python
from qitos import ToolRegistry

registry = ToolRegistry()
```

### Registering individual tools

Use `registry.register()` to add a single callable or `BaseTool` instance:

```python
@tool(name="add")
def add(a: int, b: int) -> int:
    """Add two integers."""
    return a + b

registry.register(add)
```

You can also supply a custom name or override metadata at registration time:

```python
from qitos.core.tool import ToolMeta

registry.register(add, name="math.add")
registry.register(some_func, meta=ToolMeta(description="Custom description"))
```

<Warning>
  Tool names must be unique within a registry. Registering two tools with the same name raises a `ValueError`.
</Warning>

### Scanning a module or object with `include`

`registry.include(obj)` scans all public, callable attributes of `obj` and registers any that have `@tool` metadata:

```python
class MyTools:
    @tool(name="summarize")
    def summarize(self, text: str) -> str:
        ...

    @tool(name="translate")
    def translate(self, text: str, lang: str) -> str:
        ...

tools = MyTools()
registry.include(tools)
```

This is the preferred pattern when you organize related tools as methods on a class.

### Registering toolsets

A _toolset_ is any object that has a `tools()` method returning a list of callables or `BaseTool` instances. Register it with `register_toolset()`:

```python
from qitos.kit import CodingToolSet

registry.register_toolset(
    CodingToolSet(
        workspace_root="/tmp/work",
        include_notebook=False,
        enable_lsp=False,
        enable_tasks=False,
        enable_web=False,
    )
)
```

Tools from a toolset are automatically namespaced: `toolset_name.tool_name`. You can override the namespace:

```python
registry.register_toolset(CodingToolSet(workspace_root="/tmp/work"), namespace="coding")
# registers as coding.read_file, coding.edit_file, coding.run_command, etc.
```

Built-in coding profiles expose only canonical lowercase names. Historical uppercase
and `*_v2` aliases are not registered, so prompts, permission rules, and direct registry
lookups all use the same exact names.

### Freeze one turn's tool exposure

Keep `ToolRegistry` as the mutable, run-owned catalog. At the start of every model
turn, the loop freezes it into a read-only `ToolExposure`. The model schema and the
Tool dispatcher use that same snapshot. A tool
registered while the model request is running can appear on the next turn, but it
cannot be called through the current turn's dispatcher.

The default behavior freezes every registered tool. Select a subset explicitly when
your application needs profile, capability, Skill, or policy-based selection:

```python
exposure = tool_registry.freeze(
            selected,
            metadata={"profile": state.profile},
        )
```

`group` is selection metadata, not authorization. Continue to evaluate the actual
arguments through `PermissionPipeline`. When a pipeline is configured, its
allow/deny/ask result owns admission; `needs_approval` remains the fallback for
callers without a pipeline.

Each completed model transaction records `prompt_metadata.tool_exposure`, including
the source registry revision, exact names, schema digest, and application selection
metadata. This lets journal replay explain the tool surface used for a historical
decision without treating the mutable registry as that decision's source of truth.

## `BaseTool` and `FunctionTool`

For tools that need shared state or lifecycle management, subclass `BaseTool` directly:

```python
import asyncio

from qitos.core.tool import BaseTool, ToolSpec, ToolPermission


class DatabaseTool(BaseTool):
    """Query a SQLite database."""

    def __init__(self, db_path: str):
        self.db_path = db_path
        super().__init__(
            ToolSpec(
                name="query_db",
                description="Run a SQL query and return rows as a list.",
                parameters={"sql": {"type": "string", "description": "SQL statement"}},
                required=["sql"],
                permissions=ToolPermission(filesystem_read=True),
            )
        )

    async def execute(self, args: dict, runtime_context: dict | None = None) -> list:
        _ = runtime_context
        sql = str(args["sql"])
        return await asyncio.to_thread(self._query, sql)

    def _query(self, sql: str) -> list:
        import sqlite3
        with sqlite3.connect(self.db_path) as conn:
            return conn.execute(sql).fetchall()


registry.register(DatabaseTool(db_path="data.db"))
```

`FunctionTool` is the wrapper that `register()` creates automatically when you pass a plain callable. You rarely need to instantiate it directly.

### Strict input schemas

Every registered tool has one canonical `input_schema`. QitOS projects that exact
schema to the model and validates the final, permission-adjusted arguments against it
before calling `validate_input()` or `execute()`. Validation does not coerce values:
a string such as `"2"` does not satisfy an integer field.

Generated root object schemas set `additionalProperties: false`. They reject unknown
arguments as well as missing required fields, invalid types, enum values, and JSON
Schema bounds. If a tool intentionally accepts arbitrary root keys, declare an
explicit `additionalProperties` schema (or `true`). Invalid schema definitions fail
when the tool is constructed.

`BaseTool.validate_input()` remains the hook for domain rules that JSON Schema cannot
express. It runs only after schema validation succeeds. Either validation layer can
return a terminal error without executing the handler; schema failures use
`error_category="invalid_tool_arguments"`, `attempts=0`, and `executed=false`.

Class-based tools have one asynchronous execution entry:
`await execute(args, runtime_context)`. The
registry resolves only the exact registered name and does not execute tools itself.
There are no `run`/`call` adapters, short aliases, separator aliases, or case repair.
The `ToolBatchExecutor` applies permission, timeout, retry, and
result handling uniformly. `read_only=True` describes effects; only an explicit
`concurrency_safe=True` permits parallel execution.

At turn capture, QitOS deep-copies the Tool definition while retaining the registered
handler as the single lifecycle owner. This keeps schema, timeout, permission, and
concurrency metadata stable for the turn without duplicating stateful handler counters,
background tasks, clients, or cleanup responsibility.

Synchronous decorated callables remain compatible and run outside the event loop.
Prefer `async def` for network, subprocess, Mailbox, MCP, Child, and other waiting work.
If cancellation reaches a synchronous compatibility call, QitOS waits for it to finish
before declaring the side effect terminal.

<Note>
For most practical coding agents, prefer preset toolsets such as `CodingToolSet` or the registry builders in `qitos.kit.toolset` rather than hand-registering every file and shell tool yourself.
</Note>

## Tool result contract

A plain return value is a successful tool result. A structured tool should use the
canonical lifecycle envelope when the operation is not simply complete:

```python
from qitos import ToolResult

return ToolResult(
    status="partial",
    output={"preview": text, "omitted_chars": omitted},
    artifacts=(artifact_ref,),
)
```

The canonical statuses are `success`, `partial`, `running`, `error`, `skipped`,
`denied`, `needs_input`, `needs_approval`, `timed_out`, and `cancelled`. Only exact
`success` counts as success. The boundary is strict: spellings such as `failed`,
`needs_user_input`, `output_limit_exceeded`, `cancelling`, and `canceled` are rejected
rather than normalized. Any unknown explicit status is an error, not inferred success.
Handlers do not need to manufacture correlation identity. Before finalization, the
executor copies the canonical ToolCall identity into `ToolResult.call_id`; journal replay
and traces therefore refer to the same model ToolCall.

Execution lifecycle and domain outcome are separate. For example, an empty search ran
successfully even though it found nothing:

```python
return {
    "status": "success",
    "domain_outcome": "no_match",
    "matches": [],
}
```

Do not put values such as `usable`, `pending`, or `no_match` in the top-level `status`
field. Use `needs_input` for a user question and `needs_approval` for permission to
execute. Background `running` and `partial` results remain non-successful operation
states even when the executor successfully obtained the snapshot.

### Durable long outputs

When tools can return output larger than the model budget, persist the complete
payload in a `FileArtifactStore` and return a typed `ArtifactRef` on the
`ToolResult`:

```python
from qitos.kit import FileArtifactStore

artifacts = FileArtifactStore(
    ".agent/artifacts",
    reference_root=".",
)
```

`ToolResult.output` remains canonical for journals and traces. The typed
`ToolResult.artifacts` references the durable file, while `model_output` records
the bounded projection the model actually sees; resume replays that stored
projection instead of re-applying the current size threshold.

Keep the artifact directory inside the tool workspace and set `reference_root` to that
workspace. The path shown to the model is then workspace-relative and the existing
`read_file` tool can page through it. A separate artifact-reading wrapper is not
required.

## Passing the registry to the Agent façade

Pass your populated `ToolRegistry` to the `Agent` constructor:

```python
from qitos import Agent, ToolRegistry

registry = ToolRegistry()
registry.register(web_search)
registry.register(read_file)
agent = Agent(model=model, tool_registry=registry, system_prompt="...")
```

The loop re-freezes the live registry at every turn boundary, so a Tool loaded
during one turn becomes visible to the next turn's model request. You can call
`registry.get_tool_descriptions()` to inspect the complete registered catalog.

## Full example

<CodeGroup>
```python tools.py
from qitos import tool, ToolPermission

@tool(
    name="read_file",
    timeout_s=5.0,
    permissions=ToolPermission(filesystem_read=True),
)
def read_file(path: str) -> str:
    """Read the contents of a file."""
    with open(path) as f:
        return f.read()


@tool(
    name="write_file",
    timeout_s=5.0,
    permissions=ToolPermission(filesystem_write=True),
)
def write_file(path: str, content: str) -> str:
    """Write content to a file."""
    with open(path, "w") as f:
        f.write(content)
    return f"Written {len(content)} bytes to {path}"
```

```python agent.py
import asyncio

from qitos import Agent, ToolRegistry

from .tools import read_file, write_file


async def main() -> None:
    registry = ToolRegistry()
    registry.register(read_file)
    registry.register(write_file)
    agent = Agent(model=llm, tool_registry=registry, max_turns=10)
    result = await agent.prompt("Read notes.txt and summarize it.")
    print(result.status, result.error)


asyncio.run(main())
```
</CodeGroup>
