---
title: Session journal
description: Persist complete model and tool transactions for resume and fork.
---

QitOS can persist one append-only JSONL journal per Run. When configured, the journal
is the canonical source for model history, tool transactions, state recovery, resume,
and fork. Do not configure a checkpoint store on the same Engine.

Each journal instance is one storage owner. `create()` or `open()` acquires an
operating-system writer lease for that Run. A competing process or Engine receives
`JournalOwnershipError` instead of opening a second writer. `Engine.arun()` and
`Engine.aresume_from_journal()` close their journal on every terminal path. A closed
instance rejects mutations permanently, but its isolated replay and committed-tool
query view remain available for diagnostics.

## Tool transaction order

The Engine writes each tool transaction in this order:

1. `model.completed`
2. `tool.started`
3. execute the handler
4. finalize the canonical `ToolResult`
5. `tool.terminal`
6. reduce that result into working state
7. `step.committed`

`tool.started` is a durable execution permit. If it cannot be written, the handler is
not invoked. The finalized terminal result is persisted once and is the same value used
by History and reducers. In a multi-action batch, each terminal is reduced before the
next result is finalized. Explicitly concurrency-safe handlers may still run concurrently.
The Engine binds `ToolResult.call_id` from the canonical Action before finalization and
checks that same identity during replay; older terminal records recover it from their
adjacent Action.

Finalizer or reducer failure aborts the current uncommitted transaction. Recovery uses
the durable started/terminal boundary; it never publishes a step around a missing result.

If recovery finds `tool.started` without `tool.terminal`, it writes an explicit error
terminal with unknown side effects and never runs the handler again. A call that never
received `tool.started` is closed as cancelled with no side effect. If all terminal
results exist but `step.committed` does not, recovery only reruns pure reducers.

## Shared Root/Child budget

An Engine owns a `BudgetLedger` unless a product runtime passes an existing ledger to
its constructor. Passing the Root ledger to every Child makes the complete Run tree
consume one token and cost allowance. Each Engine's `RuntimeBudget` remains a local
ceiling, so a Child can be more restricted but cannot receive a second copy of the Run
allowance.

After a provider transaction completes, the Engine appends one idempotent
`budget.committed` record to the Root JSONL before advancing the in-memory ledger.
The record includes its origin Run, model transaction, token and cost usage, and
completeness flags. Root resume and fork rebuild the shared total from these records;
SQLite is not involved. Older journals without budget records recover Root usage from
`model.completed` and completed Child usage from `child.terminal`.

`EngineResult.total_*` reports the shared Run total and `local_total_*` reports the
current Engine. `ChildResult` always stores the Child-local values, so Parent code must
not add it back into the ledger. Estimated token counts still consume the allowance but
mark usage incomplete. Cost completeness additionally requires explicit pricing and
usable input/output counts.

Settlement is serialized, but this contract does not reserve an estimate before a
provider request. Concurrent requests that already passed admission can finish above
the ceiling; the next turn stops after the committed total reaches the limit.

## State commits

`step.committed` publishes a deterministic JSON Patch subset with before and after
digests. Until that record is durable, the Engine exposes only the previous committed
state. Full snapshots are written initially, at the configured interval, and at terminal
boundaries. They accelerate replay but are not a second source of truth.

The JSONL writer waits for durable acknowledgement for every record. Darwin uses
`F_FULLFSYNC`. Other POSIX systems prefer `fdatasync` when available.

Every append first converts its payload into one isolated strict JSON value. Python
tuples become JSON arrays; non-string object keys, non-finite numbers, bytes, sets,
cycles, and custom objects are rejected before any record is written. The same value
therefore drives in-memory replay, stable-record-id settlement, JSONL encoding, reopened
replay, and projection digests.

`journal.index.sqlite3` is a disposable read projection beside the canonical file.
QitOS updates it only after the JSONL append is durable. A missing, stale, corrupt, or
unsupported projection is rebuilt from validated JSONL records. Open and replay always
parse canonical JSONL first; SQLite never supplies replay records. QitOS retains the
projection only when its record digests match those canonical records. Projection
failures do not fail or roll back a canonical append, and deleting the SQLite file loses
no Run state. Complete JSONL records with invalid semantics raise
`JournalCorruptionError`. Valid records using an unsupported old or new schema raise
`JournalUnsupportedVersionError` with upgrade or migration guidance. Both fail closed;
only an unterminated syntactically torn tail is truncated during recovery.

`JsonlRunCatalog` is the read-only side of this boundary. It can inspect or list Runs
while their writer lease remains active, and it can validate ancestor and direct-child
lineage without constructing an Agent. A catalog read uses the current complete JSONL
prefix; SQLite remains a disposable index and never supplies canonical records. The
catalog never takes a writer lease, repairs a torn tail, or rebuilds either artifact.
`RunStatus.RESUMABLE` means only that no durable `run.completed` exists; it does not
claim that an Engine process is currently active.

```python
from qitos import Engine
from qitos.kit.journal import JsonlRunCatalog, JsonlSessionJournal

journal = JsonlSessionJournal(".qitos/sessions")
result = await Engine(agent=agent, journal=journal).arun("inspect the project")

resumed = await Engine(
    agent=agent,
    journal=JsonlSessionJournal(".qitos/sessions"),
).aresume_from_journal(result.run_id)

catalog = JsonlRunCatalog(".qitos/sessions")
handle = await catalog.inspect_run(result.run_id)
all_runs = await catalog.list_runs()
ancestors = await catalog.lineage(result.run_id)
```

Forking accepts only a committed `JournalPosition`. The child journal owns an
 independent inherited prefix and can resume without its ancestors. An inherited local
 commit is itself a valid boundary, so forked Runs may be forked again. Direct
 `SessionJournal.fork()` leaves both journals open; `Engine.afork_journal()` closes its
 source and transfers the open child to the caller. If the source cannot close after the
 child is created, QitOS closes the unreturned child before propagating the source error,
 so no hidden writer lease remains. Every returned open journal remains owned by its
 caller until an Engine consumes it or `close()` is called.

## Committed tool lookup

Every canonical action result exposes a `JournalRecordRef` after its terminal record
is durable. Keep that lightweight origin locator in application state when the result
must remain discoverable after history compaction:

```python
from qitos.core.journal import JournalRecordRef

reference = JournalRecordRef(run_id=origin_run_id, record_id=terminal_record_id)
transaction = journal.find_tool_transaction(reference)
if transaction is not None:
    result = transaction.result
```

The lookup is read-only and returns a fresh typed `ToolTransaction` only after the
terminal is named by `step.committed`. Opening a journal rebuilds this query view from
its canonical JSONL records. A fork resolves inherited terminals by the parent's origin
reference, so the child does not copy the result into a second store. Unknown,
uncommitted, or child-renamed references return `None`.

Run-scoped mailbox acceptance is journal-recoverable. `runtime_input.posted` precedes
in-memory delivery, while `model.completed.runtime_input_ids` binds the exact events
seen by that transaction. Background Child and process completion inputs are deterministic
projections of their local `child.terminal` and `process.terminal` facts. `child.started`
records whether the invocation is asynchronous, so a foreground Child result is never
redelivered through the mailbox. If a process
stops after the terminal append but before `runtime_input.posted`, resume reconstructs
the same stable event and delivers it once unless a completed model transaction already
consumed its id. Forks ignore inherited terminal inputs and pending parent posts.

Child supervision writes `child.started` before constructing an Engine and
`child.terminal` before parent notification. Resume restores terminal results and closes
any start without a terminal as `interrupted`; it never reattaches or replays a Child
Engine. A terminal created during recovery is included before the resumed inbox opens.
Forks preserve inherited facts for audit but receive no control authority over parent
handles. Resuming a terminal Child for follow-up remains an application-owned Session
concern.
