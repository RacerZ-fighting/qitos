---
title: Session journal
description: Persist complete model and tool transactions for resume and fork.
---

QitOS persists one append-only JSONL journal per Run. When configured, the journal
is the canonical record of model transactions, Tool transactions, turn commits, and
run lifecycle for the minimal agent loop.

Each journal instance is one storage owner. `create()` or `open()` acquires an
operating-system writer lease for that Run. A competing process receives
`JournalOwnershipError` instead of opening a second writer. A closed instance
rejects mutations permanently, but its isolated replay and committed-tool query
view remain available for diagnostics.

## Transcript and operation records

One journal carries two record families in one sequence. Transcript entries
own message content: `transcript.message` (user, assistant and Tool-result
messages) and `compaction` (summary plus the first kept transcript reference).
Operation records own lifecycle and side-effect boundaries and reference
transcript entries by record id — message content appears in exactly one
record. `model.completed` keeps the exact request audit plus the assistant
transcript reference; `tool.terminal` keeps the call plus the terminal
transcript reference; `step.committed` is a pure commit marker listing the
turn's transcript and Tool-terminal references; `run.completed` /
`run.interrupted` carry only the terminal status and error. Records that
carry references resolve them fail closed through `journal.inherited`
wrappers.

## Loop transaction order

The loop's `JournalTurnTransaction` records each run in this order:

1. one `transcript.message` per accepted prompt, then `input.accepted`
   listing their record ids — before the first model side effect
2. the per-turn freeze diffs `model.change` / `thinking.change` /
   `tools.change` (the full trio on the first turn, diffs only afterwards)
3. `transcript.message` for the assistant message, then `model.completed`
4. `tool.started` — a durable execution permit for one admitted ToolCall
5. execute the handler and finalize the canonical `ToolResult`
6. `transcript.message` for the Tool-result message, then `tool.terminal`
7. `step.committed` — the turn commit marker

`tool.started` is a durable execution permit. If it cannot be written, the handler is
not invoked. The finalized terminal result is persisted once and is the same deeply
immutable value delivered to the transcript. Parallel Tool batches commit results in
input order, and every admitted call receives exactly one terminal result, including
denied, timed-out, and cancelled calls.

A run ends in exactly one terminal record: `run.completed` carries the terminal
status (`completed`, `failed`, `max_turns`, `deadline_exceeded`); an aborted run
appends `run.interrupted` instead. External task
cancellation and faults terminalize started work and the run record before
re-raising, so a run never ends without a terminal record.

## Recovery

`recover_session(records)` replays one journal into the typed transcript, the
compaction-projected context, the configuration lineage (model, thinking
level, active Tools, including Tools activated by earlier Tool results), open
Tool operations, unconsumed runtime inputs and the terminal outcome. It is a
pure function over one journal's replay — inherited fork prefixes resolve
through their wrappers, so one forked journal is self-contained recovery
truth — and it fails closed with `JournalCorruptionError` on contradictions:
dangling transcript references, a Tool transcript entry without its
`tool.terminal`, commits or run terminals covering open calls, unknown commit
references, conflicting run terminals, records after a run terminal,
regressing turns, invalid compaction cuts, or retired Engine-era payload
shapes.

A Tool call admitted but never terminated, or never admitted at all, is the
legitimate crash window when no commit or run terminal covers it.
`close_crashed_tool_calls(journal, recovered)` closes that window without
re-executing anything and without guessing side effects: each call receives
an explicit cancelled `tool.terminal` plus its transcript entry (a torn
durable entry is linked, never replaced) and one closing `step.committed`.
The synthesized errors distinguish "started, outcome unknown" from "never
admitted, no side effects". Record ids and payloads are deterministic
functions of the recovered journal, so closing twice never double-appends.

`InMemorySessionJournal` implements the same `SessionJournal` contract in
memory — durability scoped to a shared `InMemoryJournalStore` — and shares
one conformance suite with the JSONL implementation. Consumption of a posted
runtime input is journaled as `runtime_input.consumed`, so unconsumed inputs
re-project exactly once on recovery while inherited fork facts are never
redelivered.

## Session Harness

`qitos.kit.session.SessionHarness` is the authoritative owner of the Session
lifecycle over these journals. It is constructed with a journal home — a
directory of JSONL journals or a shared `InMemoryJournalStore` — plus optional
`CompactionSettings` and an optional trace directory.

```python
from qitos.kit.session import SessionHarness

harness = SessionHarness(".qitos/sessions")
session = await harness.start(model=model, tool_registry=registry)
result = await session.prompt("Investigate the staging deployment")
await session.close()
```

`resume(run_id, ...)` continues an unfinished journal in place: it replays the
journal through pure recovery, closes a crash window with explicit cancelled
terminals (never re-executing), restores the context messages, thinking level
and configuration lineage into a fresh `Agent`, and re-projects each
unconsumed runtime input exactly once. Expected mismatches return a typed
`ResumeRejected` instead of raising: `not_found`, `terminal` (fork is the
explicit continuation), `model_mismatch` (the journaled
provider/model/api identity differs from the provided model), `tools_missing`
(the journaled active Tools, including Tools activated by earlier Tool
results, are absent from the provided registry — the names are included), and
`busy` (another writer holds the lease). Corruption raises
`JournalCorruptionError`; Tool objects are never reconstructed from the
journal.

`fork(run_id, position=None, ...)` branches a journal at a committed boundary
— the latest one by default — into a new self-contained journal that embeds
the inherited prefix. A fork of a terminal run is the explicit way to continue
finished work, and inside one `SessionRun` a prompt after the current leg
settles advances along the same fork mechanism, so every journal stays
append-only while the session stays interactive. One Run journal accepts one
`input.accepted`; a new prompt into a resumed journal enters as steering
before the next turn instead.

Compaction follows Pi's proven algorithm: `compact()` runs at idle only
(typed rejections for `busy` and `nothing_to_compact`), the cut never lands
on a Tool result or between a Tool call and its result, a split turn merges a
turn-prefix summary, and iterative compactions fold the previous summary into
the new one. The summary is generated by the run's own model with one bounded
request and no Tool exposure, persisted as a durable `compaction` record
(with summarization usage when available), and projected into the façade by
replacing the transcript — which also seals Provider continuation so the next
request is a full request. With `CompactionSettings` configured, the harness
also evaluates the token threshold at idle boundaries against the model's
`context_window`, and performs one compact-and-continue attempt after a
context-overflow model failure.

## Durability and projections

The JSONL writer waits for durable acknowledgement for every record. Darwin uses
`F_FULLFSYNC`. Other POSIX systems prefer `fdatasync` when available.

Every append first converts its payload into one isolated strict JSON value. Python
tuples become JSON arrays; non-string object keys, non-finite numbers, bytes, sets,
cycles, and custom objects are rejected before any record is written. The same value
therefore drives in-memory replay, stable-record-id settlement, JSONL encoding, and
reopened replay.

`journal.index.sqlite3` is a disposable read projection beside the canonical file.
QitOS updates it only after the JSONL append is durable. A missing, stale, corrupt, or
unsupported projection is rebuilt from validated JSONL records. Open and replay always
parse canonical JSONL first; SQLite never supplies replay records. Complete JSONL
records with invalid semantics raise `JournalCorruptionError`. Valid records using an
unsupported old or new schema raise `JournalUnsupportedVersionError`. Both fail
closed; only an unterminated syntactically torn tail is truncated during recovery.

`JsonlRunCatalog` is the read-only side of this boundary. It can inspect or list Runs
while their writer lease remains active, and it can validate ancestor and direct-child
lineage without constructing an Agent. A catalog read uses the current complete JSONL
prefix; SQLite remains a disposable index and never supplies canonical records.
`RunStatus.RESUMABLE` means only that no durable `run.completed` exists.

Each `RunHandle` also exposes a stable `lineage_id`, the immediate `parent_run_id`,
the latest durable `committed_position`, a `continuation_position`, and
`has_terminal_state`.

```python
from qitos.kit.journal import JsonlRunCatalog, JsonlSessionJournal

catalog = JsonlRunCatalog(".qitos/sessions")
handle = await catalog.inspect_run(run_id)
all_runs = await catalog.list_runs()
ancestors = await catalog.lineage(run_id)

if handle.is_terminal and handle.continuation_position is not None:
    source = JsonlSessionJournal(".qitos/sessions")
    await source.open(handle.run_id)
    child = await source.fork(handle.continuation_position, "follow-up-run")
    await child.close()
    await source.close()
```

Forking accepts only a committed `JournalPosition`. The child journal owns an
independent inherited prefix and can resume without its ancestors. An inherited local
commit is itself a valid boundary, so forked Runs may be forked again. Every returned
open journal remains owned by its caller until `close()` is called.

## Committed tool lookup

Every canonical Tool terminal is discoverable through a lightweight
`JournalRecordRef` locator once its terminal record is durable:

```python
from qitos.core.journal import JournalRecordRef

reference = JournalRecordRef(run_id=origin_run_id, record_id=terminal_record_id)
transaction = journal.find_tool_transaction(reference)
if transaction is not None:
    result = transaction.result
```

The lookup is read-only and returns a fresh typed `ToolTransaction` only after the
terminal is named by a `step.committed` record; the result is joined from the
referenced `transcript.message` record, fail closed on a missing or mismatched
reference. Opening a journal rebuilds this query
view from its canonical JSONL records. A fork resolves inherited terminals by the
parent's origin reference, so the child does not copy the result into a second store.
Unknown, uncommitted, or child-renamed references return `None`. Only the loop's
record schema is decodable; records written by the retired Engine taxonomy fail
closed.

## Child and mailbox records

Child supervision writes `child.started` before constructing the child Agent and
`child.terminal` before parent notification. Recovery rebuilds a started child from
its own loop journal when that journal holds a durable run terminal record, and
closes it as `interrupted` otherwise; it never reattaches or replays a child Agent.
A terminal created during recovery is persisted before the supervisor reports
recovered results. Forks preserve inherited facts for audit but receive no control
authority over parent handles.

Parent messages to an active child are journaled as `runtime_input.posted` before
the message enters the child run's steering queue, so mailbox acceptance is
journal-recoverable and the message becomes visible at the child's next turn safe
point. Once the steered message enters the committed transcript, the child engine
appends the idempotent `runtime_input.consumed` record; a run that ends without
injecting the message consumes nothing.
