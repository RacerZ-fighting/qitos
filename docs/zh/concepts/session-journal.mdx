QitOS 为每个 Run 保存一份 append-only JSONL Journal。启用后，它是最小 agent loop 的
模型事务、工具事务、turn 提交与运行生命周期的 canonical 记录。

每个 Journal 实例都是唯一的存储 owner。`create()` 或 `open()` 会取得该 Run 的操作系统级
writer lease；其他进程若尝试同时写入，会得到 `JournalOwnershipError`，而不是打开
第二个 writer。关闭后的实例永久拒绝修改，但仍可从隔离的内存值 replay 或查询已提交工具事务，
便于诊断。

## Loop 事务顺序

loop 的 `JournalTurnTransaction` 按以下顺序记录每个 turn：

1. `model.completed`：一次已终结的模型事务（成功或失败）
2. `tool.started`：一次已准入 ToolCall 的持久化执行许可
3. 执行 Handler
4. 生成唯一 canonical `ToolResult`
5. `tool.terminal`
6. `step.committed`：该 turn 提交的消息，以及链接其 Tool 终态记录的
   `terminal_record_ids`

`tool.started` 是持久化执行许可；写入失败时不能执行 Handler。终态结果只持久化一次，
并且与进入 transcript 的值是同一个深度不可变值。并行 Tool 批次按输入顺序提交结果，
每个已准入调用（包括拒绝、超时、取消）都恰好得到一个终态结果。

一次运行恰好以一个终态记录结束：`run.completed` 携带终态状态（`completed`、`failed`、
`max_turns`、`deadline_exceeded`）与本次运行新增的消息；被中止的运行改为写入
`run.interrupted`。外部任务取消与故障会先终结已开始的工作和运行记录再重新抛出，
因此一次运行永远不会缺少终态记录。

## 持久化与投影

JSONL writer 每条记录都等待持久化确认。Darwin 使用 `F_FULLFSYNC`；其他 POSIX 系统优先
使用 `fdatasync`。

每次追加都会先把载荷转换为一份隔离的严格 JSON 值：Python 元组变成 JSON 数组；
非字符串键、非有限数值、bytes、集合、循环引用和自定义对象都会在写入前被拒绝。同一个值
因此同时驱动内存 replay、稳定 record id 结算、JSONL 编码与重新打开后的 replay。

`journal.index.sqlite3` 是 canonical 文件旁的一次性读投影。QitOS 只在 JSONL 追加持久化后
更新它。缺失、过期、损坏或版本不符的投影会从校验过的 JSONL 记录重建。打开与 replay 永远
先解析 canonical JSONL；SQLite 不提供 replay 记录。语义无效的完整记录抛出
`JournalCorruptionError`；schema 过旧或过新的有效记录抛出
`JournalUnsupportedVersionError`。两者都 fail closed；只有未终止的尾部撕裂会在恢复时截断。

`JsonlRunCatalog` 是这个边界的只读一侧。它可以在 writer lease 仍活跃时检查或列出 Run，
也可以在不构造 Agent 的情况下校验祖先与直接子代 lineage。catalog 读取使用当前完整 JSONL
前缀；SQLite 只是一次性索引，绝不提供 canonical 记录。`RunStatus.RESUMABLE` 只表示没有
持久化的 `run.completed`。

每个 `RunHandle` 还暴露稳定的 `lineage_id`、直接父级 `parent_run_id`、最新的持久化
`committed_position`、`continuation_position` 和 `has_terminal_state`。

```python
from qitos.kit.journal import JsonlRunCatalog, JsonlSessionJournal

catalog = JsonlRunCatalog(".qitos/sessions")
handle = await catalog.inspect_run(run_id)
all_runs = await catalog.list_runs()
ancestors = await catalog.lineage(run_id)

if handle.is_terminal and handle.continuation_position is not None:
    source = JsonlSessionJournal(".qitos/sessions")
    await source.open(handle.run_id)
    child = await source.fork(handle.continuation_position, "follow-up-run")
    await child.close()
    await source.close()
```

fork 只接受已提交的 `JournalPosition`。子 journal 拥有独立的继承前缀，可以在没有祖先的
情况下恢复；继承来的本地提交本身也是有效边界，因此 fork 出的 Run 可以再次 fork。
每个返回的打开 journal 都由调用方持有，直到调用 `close()`。

## 已提交工具查询

每个 canonical Tool 终态记录在持久化后都可以通过轻量 `JournalRecordRef` 定位：

```python
from qitos.core.journal import JournalRecordRef

reference = JournalRecordRef(run_id=origin_run_id, record_id=terminal_record_id)
transaction = journal.find_tool_transaction(reference)
if transaction is not None:
    result = transaction.result
```

该查询是只读的，只有在终态记录被 `step.committed` 点名后才返回新的类型化
`ToolTransaction`。打开 journal 时会从 canonical JSONL 记录重建这份查询视图。fork 通过
父级来源引用解析继承的终态记录，子级不会把结果复制到第二个存储。未知、未提交或被
子级改名的引用返回 `None`。只有 loop 的记录 schema 可以解码；旧 Engine taxonomy 写入的
记录会 fail closed。

## Child 与 mailbox 记录

Child 监督在构造子 Agent 之前写入 `child.started`，在通知父级之前写入 `child.terminal`。
恢复时，如果子级自己的 loop journal 中存在持久化运行终态记录，就从该 journal 重建子级
终态结果，否则将其关闭为 `interrupted`；恢复永远不会重新挂载或重放子 Agent。恢复期间
创建的终态记录会在 supervisor 报告恢复结果之前持久化。fork 保留继承的事实用于审计，
但不会获得对父级 handle 的控制权。

发给活跃子级的父级消息会先作为 `runtime_input.posted` 写入 journal，再进入子级运行的
steering 队列，因此 mailbox 接收可以从 journal 恢复，消息会在子级下一个 turn 安全点可见。
