QitOS 的配置主要分三层：

1. **`AgentModule.run()` 关键字参数**：最常见、最推荐的每次运行配置入口
2. **`Engine` 构造函数参数**：更底层的运行时控制
3. **环境变量**：供应商凭证与模型默认值

## OpenAI 传输模式

`OpenAIModel`、`OpenAICompatibleModel` 及其异步版本支持两种显式传输模式：

| `api_mode` | 行为 |
|---|---|
| `chat_completions` | 默认值。使用 `/v1/chat/completions`，保持现有 QitOS 行为 |
| `responses` | 可选启用。使用 `/v1/responses`，保留有序原生输出项，并通过 `call_id` 关联函数调用与工具结果 |

YAML 配置示例：

```yaml
model:
  provider: openai
  model: gpt-5
  api_mode: responses
```

也可以直接构造模型：

```python
from qitos.models import OpenAIModel

llm = OpenAIModel(
    model="gpt-5",
    api_mode="responses",
)
```

Responses 模式支持同步、异步和类型化流式调用。工具循环期间，QitOS 会重放供应商返回的有序输出项以及 `function_call_output`，无需在模型适配器中维护可变的 `previous_response_id`。历史压缩不会拆散仍在执行的原生工具调用轮次。

<Warning>
不同 OpenAI 兼容端点可能只实现 `/v1/responses` 的一部分。Responses 请求失败后，QitOS 不会静默回退到 Chat Completions；不支持 Responses 的端点应显式使用 `chat_completions`。
</Warning>

Reasoning item 被视为不透明的续接状态。追踪摘要只保留安全的 item 描述与供应商允许的摘要，并排除加密 reasoning 续接内容。

### Reasoning 强度与续接

`build_model_for_preset(...)` 接受统一的 `reasoning_effort`：`low`、`medium`、
`high`、`xhigh` 或 `max`。QitOS 会根据所选模型族只解析一次，并让同步、异步和
流式请求共用解析后的请求默认值。不受支持的级别会映射到最接近的已声明级别；
例如 GPT-5.6 会保留 `max`，较旧的 OpenAI policy 则上限为 `xhigh`。

对于官方 OpenAI Responses 请求，QitOS 会请求 `reasoning.encrypted_content`，
保留 output-item 事件先于最终响应送达的字段，并在下一轮工具调用中按顺序原样重放。
Kimi 等兼容供应商不会收到这个 OpenAI 专属的 `include` 值。兼容 Chat 返回的
`reasoning_content` 只作为续接元数据保存，不会在可见答案为空时被冒充为最终回答。

### 模型重试与 Engine deadline

`OpenAIModel`、`OpenAICompatibleModel` 及其异步版本共用同一传输实现。
OpenAI SDK 的内置重试固定关闭，`ModelRetryPolicy` 是唯一重试 owner。Engine 会把
相对或绝对运行时限制绑定成一次逻辑模型请求的 deadline；每次 attempt 都按实时剩余
时间收紧 provider timeout，backoff 同时响应 deadline 与立即取消。无法中断的同步
provider 会留在 daemon worker 中，其迟到结果会被丢弃，不能写入 history、action 或
final state。

所有模型流都使用 `ModelStreamChunk` 作为统一契约。终态 chunk 会保留供应商实际的
`finish_reason`，文本、reasoning、类型化事件元数据、完整工具调用、原生 item 与 usage
保持为独立字段。Chat 工具参数分片使用 `event_type="tool_call.delta"`；Responses 则
保留供应商事件类型和序列元数据。若供应商在终态事件前关闭流，QitOS 会抛出
`ModelTransportError`，不会伪造成功完成。原有 Engine handler 仍只需实现
`on_start/on_delta/on_end`；需要完整观察能力时可选实现 `on_chunk(chunk)` 和
`on_error(exc)`。

## AgentModule.run() 参数

这些参数都可以直接传给 `agent.run(task, ...)`：

<AccordionGroup>
<Accordion title="任务与执行">

- `task`：`str | Task`
- `max_steps`
- `return_state`
- `workspace`
- `env`

</Accordion>

<Accordion title="解析与决策">

- `parser`
- `search`
- `critics`（评估器，可批准、停止或重试当前步骤）
- `stop_criteria`
- `history_policy`

</Accordion>

<Accordion title="追踪与渲染">

- `trace`
- `trace_logdir`
- `trace_prefix`
- `render`
- `theme`

</Accordion>

<Accordion title="钩子与 Engine 透传">

- `hooks`
- `render_hooks`
- `engine_kwargs`
- `**state_kwargs`

</Accordion>
</AccordionGroup>

一个典型例子：

```python
result = agent.run(
    task="Analyse the repository and list all public API functions.",
    workspace="/path/to/repo",
    max_steps=20,
    trace_logdir="./experiment-runs",
    trace_prefix="api-analysis",
)
```

## Engine 构造参数

当你直接构造 `Engine` 时，最常用的参数包括：

- `agent`
- `budget`（预算）
- `validation_gate`
- `recovery_handler`
- `recovery_policy`
- `trace_writer`
- `parser`
- `stop_criteria`
- `branch_selector`
- `search`
- `critics`（评估器）
- `env`
- `history_policy`
- `hooks`（钩子）

`RuntimeBudget` 的常见字段：

```python
@dataclass
class RuntimeBudget:
    max_steps: int = 10
    max_runtime_seconds: Optional[float] = None
    max_tokens: Optional[int] = None
    deadline_monotonic: Optional[float] = None
```

`max_runtime_seconds` 从 Engine 接纳运行时开始计时；`deadline_monotonic` 是外层调度器
按 `time.monotonic()` 传入的绝对截止时间，不会把排队消耗的时间重新补回来。两者同时
存在时取更早者。`Task` 可以覆盖相对预算，但不会移除外层绝对截止时间。

## 环境变量

常见环境变量包括：

| 变量 | 用途 |
|---|---|
| `OPENAI_API_KEY` | OpenAI / OpenAI 兼容 API 密钥 |
| `OPENAI_BASE_URL` | OpenAI 兼容端点基础 URL |
| `QITOS_API_KEY` | `ModelFactory.from_env()` 可识别的备用密钥 |
| `QITOS_MODEL` | 默认模型 ID |
| `AZURE_OPENAI_API_KEY` | Azure OpenAI 密钥 |
| `AZURE_OPENAI_ENDPOINT` | Azure OpenAI 端点 |
| `AZURE_OPENAI_DEPLOYMENT` | Azure 部署名称 |
| `AZURE_OPENAI_API_VERSION` | Azure API 版本 |

示例：

```bash
OPENAI_API_KEY=sk-...
OPENAI_BASE_URL=https://api.siliconflow.cn/v1/
```

## 追踪输出目录

默认情况下，`AgentModule.run()` 会把追踪记录写到 `./runs/`：

```text
<trace_logdir>/
└── <trace_prefix>_<YYYYMMDD_HHMMSS_ffffff>/
    ├── manifest.json
    ├── events.jsonl
    └── steps.jsonl
```

你可以通过 `trace_prefix` 覆盖自动生成的前缀：

```python
agent.run(task="...", trace_prefix="experiment-01")
```

然后用：

```bash
qita board --logdir ./runs
```

来查看这些结果。
