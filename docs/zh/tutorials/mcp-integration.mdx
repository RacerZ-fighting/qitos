---

Model Context Protocol（MCP）是一个开放标准，用于将 AI 系统连接到外部工具和数据源。QitOS 可以为完整的 `Engine.arun()` 或交互式 `Engine.astep()` session 持有 MCP 生命周期：第一轮模型请求前发现工具，在调用方 event loop 上异步执行调用，并在 owner 结束时移除工具和关闭 transport。

## 推荐：由 Engine 持有每个 Run 的生命周期

给 Agent 配置 `ToolRegistry`，再向 `Engine` 传入一个只负责构造的 factory；每次
Run 都必须返回全新且尚未连接的 transport：

```python
from qitos import Engine, ToolRegistry
from qitos.mcp import MCPServerStdio

def create_mcp_servers():
    return (
        MCPServerStdio(
            command="npx",
            args=["-y", "@modelcontextprotocol/server-filesystem", "/workspace"],
            name="filesystem",
        ),
    )

agent = MyAgent(tool_registry=ToolRegistry())
engine = Engine(agent, mcp_server_factory=create_mcp_servers)
result = await engine.arun("检查 workspace")
```

模型看到的是 `mcp__filesystem__read_file` 这类 provider-safe 名称；QitOS 仍保留服务器与工具的原始名称来发起协议调用。模型可见名称会经过字符清理、冲突消解，并限制为 64 个字符。注册只在当前 run 生效，因此后续 Engine 可以复用同一个 registry。

`mcp_server_factory=None` 是正常默认值，不会创建 MCP 子进程或 HTTP client。
Factory 只能构造对象；真正的 I/O 由 `connect()` 在 Run deadline 内完成。不能返回共享的
client 或进程：Root、Child、resume 以及后续 Run 都应持有独立 transport。配置发现、
catalog 和审批策略仍由应用层决定。

Run 启动时，QitOS 会并发连接独立 server 并发现目录，默认最多同时执行八个 startup
操作。每个 server 最多使用 10 秒或 Run 剩余 deadline，以较短者为准。单个 server
失败后会独立清理，不会取消健康 server；成功目录仍按 factory 顺序转换和发布，因此
模型看到的 Tool 列表保持确定性。

每轮模型请求都会冻结一份 Tool exposure。协议
`notifications/tools/list_changed` 通知或显式调用
`engine.request_mcp_refresh(server_name)`，只会把已连接目录标记为在下一次 turn
前安全点刷新。完整的新目录只从下一轮开始发布；当前轮仍使用原来的 handler 和
schema。刷新失败会保留上一版完整目录；刷新被取消时取消会继续向上传播，同时保留待刷新状态。

交互式 session 使用同一个 owner。`init_session()` 只创建 session state；第一次
`await engine.astep(...)` 会在捕获 turn 前启动 MCP，后续 `astep()` 会在各自 turn
快照前应用待处理 refresh。所有 step 与 `aclose()` 都应留在启动 transport 的同一个
event loop。同步 `engine.step(...)` 会拒绝 MCP session，因为临时 event loop 无法持有
持久 transport。

Stepwise API 不管理 durable Run Journal 或 checkpoint commit。需要让模型与 Tool
事务在进程重启后继续恢复时，请使用 `arun()`、`resume()` 和 `fork()`。

Engine 只执行来自完整模型事务的 MCP ToolCall。已知 incomplete、达到长度上限、failed、
filtered 或 cancelled 的终态会把原生或文本恢复出的调用保留为
`invalid_tool_calls` 诊断，但绝不会执行。

## Transport 选项

QitOS 内置两种传输实现。对于以命令行进程方式运行的本地 MCP 服务器，使用 `MCPServerStdio`：

```python
from qitos.mcp import MCPServerStdio

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)
await server.connect()
```

对于提供 HTTP 端点的远程 MCP 服务器，使用 `MCPServerStreamableHttp`：

```python
from qitos.mcp import MCPServerStreamableHttp

server = MCPServerStreamableHttp(
    url="http://localhost:8080/mcp",
    headers={"Authorization": "Bearer token123"},
)
await server.connect()
```

两种传输都会在 `connect()` 期间自动完成 MCP 初始化握手。连接成功后，可以列出可用工具：

```python
tools = await server.list_tools()
for tool in tools:
    print(f"  {tool.name}: {tool.description}")
```

两种 transport 都会按有界的 `nextCursor` 分页读取目录，不会静默只返回第一页。
`list_tools()` 返回的每一项都是官方 `mcp.types.Tool`，包含 `name`、
`description`、`inputSchema` 和类型化 MCP `annotations`。Annotation 只是不可信提示：缺失
`readOnlyHint` 不会被解释为只读，QitOS 也不会据此推断并发安全或允许重试。

两种 transport 都直接使用官方 `mcp` Python SDK 完成 framing、校验、初始化、通知分发
和关闭。Stdio 只继承 SDK 的安全环境变量白名单以及通过 `env=` 显式传入的变量。由于 SDK
context 必须由进入它的同一个 task 退出，QitOS 会为每个连接持有一个 run-owned task。

## 底层桥接

`mcp_server_to_function_tools` 函数将已连接的 MCP 服务器上的每个工具转换为 `FunctionTool` 实例。它适合自行持有连接与 transport event loop 的应用；普通 Agent 应优先使用上面的 Engine 路径。

```python
from qitos.mcp import MCPServerStdio, mcp_server_to_function_tools

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)
await server.connect()

tools = await mcp_server_to_function_tools(server)
```

每个返回的 `FunctionTool` 封装了一次远程 MCP 调用。工具执行时，QitOS 会发送
`tools/call` JSON-RPC 请求，并把官方 `mcp.types.CallToolResult` 投影为普通 QitOS
`ToolResult`。`structuredContent`、`_meta` 和 content block 会被保留；
`isError=true` 会成为 `ToolResult(status="error")`，不会伪装成成功 JSON 值。
JSON-RPC 协议错误、远端请求错误、远端 Tool 错误、timeout 和 cancellation 仍是可区分的终态。

官方 Streamable HTTP transport 支持 JSON 或 SSE，并保留协商得到的 session header。
Session 终止会稳定分类为 `MCP_SESSION_EXPIRED`。QitOS 可以在下一轮安全点重新连接并重复
无副作用的 catalog discovery，但不会自动重放可能产生副作用的 `tools/call`。

当需要将多个服务器桥接到同一注册表时，可以添加名称前缀来消除歧义：

```python
fs_tools = await mcp_server_to_function_tools(server, name_prefix="fs")
# 工具名称变为：fs__read_file、fs__write_file 等
```

像注册其他工具一样，将桥接后的工具注册到 `ToolRegistry`：

```python
from qitos import ToolRegistry

registry = ToolRegistry()
for tool in fs_tools:
    registry.register(tool)
```

## 在应用自管桥接中筛选工具

MCP 服务器通常暴露很多工具，但你的智能体可能只需要其中一部分。`ToolFilter` 控制哪些工具会被桥接：

**仅允许特定工具：**

```python
from qitos.mcp import ToolFilter, mcp_server_to_function_tools

tool_filter = ToolFilter(allowed_tool_names={"read_file", "list_directory"})
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

**阻止特定工具：**

```python
tool_filter = ToolFilter(blocked_tool_names={"delete_file", "move_file"})
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

**自定义过滤函数：**

```python
tool_filter = ToolFilter(filter_func=lambda name: name.startswith("read_"))
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

可以同时组合允许列表和阻止列表。工具名必须在允许列表中（如果设置了的话）且不在阻止列表中：

```python
tool_filter = ToolFilter(
    allowed_tool_names={"read_file", "write_file", "delete_file"},
    blocked_tool_names={"delete_file"},
)
# 只有 read_file 和 write_file 通过
```

评估顺序如下：

1. 如果设置了 `filter_func`，其返回值为最终结果。
2. 如果设置了 `allowed_tool_names`，只有集合中的名称通过。
3. 如果设置了 `blocked_tool_names`，集合中的名称被排除。
4. 否则名称通过（无过滤）。

## 应用自管的异步生命周期

MCP 服务器连接持有资源（子进程、HTTP 客户端），必须进行清理。务必将 `connect()` 与 `cleanup()` 配对使用：

```python
from qitos.mcp import MCPServerStdio, mcp_server_to_function_tools, ToolFilter

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)

try:
    await server.connect()

    tools = await mcp_server_to_function_tools(
        server,
        tool_filter=ToolFilter(blocked_tool_names={"dangerous_op"}),
        name_prefix="fs",
    )

    # 在智能体中使用工具...
    for tool in tools:
        print(f"Bridged: {tool.spec.name}")

finally:
    await server.cleanup()
```

`MCPServerStdio.cleanup()` 遵循 SDK 的关闭流程：关闭 server 输入、等待优雅退出，必要时
终止所持有的进程树。`MCPServerStreamableHttp.cleanup()` 会终止协商得到的 session 并关闭
HTTP client。QitOS 会先停止接纳新调用，等待已经开始的调用收敛，再由专用 owner task
退出两个 SDK context。调用方取消仍会继续向上传播，不会创建第二个 event loop，也不会
重放 Tool 调用。

Bridge、transport 与 Engine 都运行在调用方 event loop 上，不会创建临时或独立的
MCP event loop。因此 bridged Tool 运行期间，应用代码不能阻塞该 loop。
