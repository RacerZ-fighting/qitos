# Checkpoint 恢复与 Journal 分支

QitOS checkpoint 保存 Agent 状态 snapshot，用于中断后的恢复。Session Journal 保存完整的
模型与 Tool 事务，并拥有可执行 Run 的分支语义。一个 Engine 只能选择一种持久化模式；不要同时
配置 checkpoint store 和 Journal。

这对以下场景至关重要：
- **长时间运行的任务**，可能被中断（网络错误、预算限制）
- **分支实验**，从已提交的 Journal boundary 继续执行
- **lineage 检查**，查询 Parent 与 Child Run

## Step 1: 基本检查点

创建 `CheckpointStore` 并配置 Engine 使用它：

```python
from qitos.checkpoint import InMemoryCheckpointStore, CheckpointConfig

# 创建内存存储（使用 SqliteCheckpointStore 进行持久化）
store = InMemoryCheckpointStore()

# 传递给 Engine
from qitos.engine import Engine
from my_agent import MyAgent

agent = MyAgent()
engine = Engine(agent, checkpoint_store=store, auto_approve=True)

# 运行 Agent — 检查点自动保存
result = await engine.arun("分析数据集")

# 访问最新检查点
config = CheckpointConfig(thread_id=result.run_id)
latest = await store.get_tuple(config)
print(f"Checkpoint at step {latest.checkpoint.step}")
```

`engine.last_checkpoint_id` 是只读的生命周期状态。首次 checkpoint 成功提交前它为
`None`；只有 `CheckpointStore.put()` 成功后才会推进；resume 时则初始化为来源
checkpoint 的 ID。Hook 可以在安全边界比较这个值，无需访问 Engine 私有字段。

跨会话持久化存储，使用 `SqliteCheckpointStore`：

```python
from qitos.checkpoint import SqliteCheckpointStore

store = SqliteCheckpointStore("./checkpoints.db")
```

## Step 2: 恢复运行

如果运行被中断，从上次检查点恢复：

```python
from qitos.checkpoint import CheckpointConfig

# thread_id 标识运行（通常是 run_id）
config = CheckpointConfig(thread_id="my-run-001")

# 从状态和完整模型历史快照恢复运行
result = await engine.aresume_from_checkpoint(config)
```

Engine 从最新检查点恢复状态，从中断处继续执行。

如果选中的 checkpoint 已经进入终态，Engine 会直接返回持久化状态，不再发起模型请求、
工具调用或新 checkpoint。若恢复用的 Engine 配置了新的 `TraceWriter`，QitOS 会用已保存的
停止原因和结果正确结束这份空 trace。

## Step 3: 分叉 Journal Run

需要可执行分支时，应创建 Journal-backed Run，并且只从已提交的 continuation position
进行 fork：

```python
from qitos import Engine
from qitos.kit.journal import JsonlRunCatalog, JsonlSessionJournal

journal_root = ".qitos/sessions"
run = await Engine(
    MyAgent(),
    journal=JsonlSessionJournal(journal_root),
    auto_approve=True,
).arun("分析数据集")

catalog = JsonlRunCatalog(journal_root)
handle = await catalog.inspect_run(run.run_id)
boundary = handle.continuation_position
if boundary is None:
    raise RuntimeError("Run 没有已提交的 continuation boundary")

child_run_id = "my-run-001-branch-a"
child_journal = await Engine(
    MyAgent(),
    journal=JsonlSessionJournal(journal_root),
    auto_approve=True,
).afork_journal(
    handle.run_id,
    boundary,
    new_run_id=child_run_id,
)

# 恢复独立 Child，不重放已提交的 Tool。
branch_result = await Engine(
    MyAgent(),
    journal=child_journal,
    auto_approve=True,
).aresume_from_journal(child_run_id)
```

原始 Run 不受影响。Child 拥有独立的 inherited prefix；即使祖先文件之后不可用，仍可恢复。

## Step 4: 检查 Run Lineage

只读 catalog 无需取得 writer lease 或创建 Engine，就能查询祖先与直接 Child：

```python
lineage = await catalog.lineage(child_run_id)
children = await catalog.children(handle.run_id)
print([item.run_id for item in lineage])
print([item.run_id for item in children])
```

Terminal Run 的 resume 始终只读；需要继续工作时，应把它的非终态
`continuation_position` 显式 fork 到新的 Run id。

## Step 5: 持久化边界

全新运行的 `Engine.arun()` 会在第一次 Provider 请求前等待一个 `input` checkpoint，保存已
初始化的任务、状态和历史。之后的完整 step checkpoint 以该输入边界为父级。恢复这个输入
checkpoint 会重新执行 step zero，但不会再次写入 `input` checkpoint。

Engine 也会在每个完整 step 结束后等待 `CheckpointStore.put()`。写入成功前，该 step 不算
持久化完成。SQLite 操作在线程外执行；取消发生时，会先等待正在执行的数据库调用稳定结束，
再继续传播取消。每个 store 实例只属于一个 event loop；内存与 SQLite store 接受相同的 JSON
可序列化数据。

## Step 6: 检查快照

每个 checkpoint 保存 checkpoint resume 所需的状态、原始任务、完整模型历史前缀与
snapshot 父级：

```python
config = CheckpointConfig(thread_id="my-run-001")
tuple_ = await store.get_tuple(config)
print(tuple_.checkpoint.task_text)
print(tuple_.checkpoint.history.messages)
```
