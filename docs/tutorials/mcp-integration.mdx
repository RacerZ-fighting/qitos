The Model Context Protocol (MCP) is an open standard for connecting AI systems to external tools and data sources. QitOS can own MCP servers for a complete `Engine.arun()` or an interactive `Engine.astep()` session: it discovers tools before the first model turn, executes calls asynchronously on the caller's event loop, and removes tools and closes transports when the owner ends.

## Preferred: let Engine own each Run lifecycle

Give the agent a `ToolRegistry`, then pass `Engine` a construction-only factory that
returns fresh, unconnected transports for every Run:

```python
from qitos import Engine, ToolRegistry
from qitos.mcp import MCPServerStdio

def create_mcp_servers():
    return (
        MCPServerStdio(
            command="npx",
            args=["-y", "@modelcontextprotocol/server-filesystem", "/workspace"],
            name="filesystem",
        ),
    )

agent = MyAgent(tool_registry=ToolRegistry())
engine = Engine(agent, mcp_server_factory=create_mcp_servers)
result = await engine.arun("Inspect the workspace")
```

The model sees provider-safe names such as `mcp__filesystem__read_file`; QitOS preserves the raw server and tool names for protocol calls. Names are sanitized, deduplicated, and bounded to 64 characters. Registrations are run-scoped, so the same registry can be reused by a later Engine run.

`mcp_server_factory=None` is the normal default. It starts no MCP subprocess or HTTP
client. The factory must only construct objects; `connect()` performs I/O under the
Run deadline. Do not return a shared client or process: Root, Child, resumed, and later
Runs each own independent transports. Configuration discovery, catalogs, and approval
policy remain application concerns.

At Run startup, QitOS connects and discovers independent servers concurrently, with
at most eight startup operations active by default. Each server gets at most 10 seconds
or the remaining Run deadline, whichever is shorter. A failed server is cleaned up
without cancelling healthy servers. Successful catalogs are still converted and
published in factory order, so the model-visible Tool list is deterministic.

Each model turn freezes one Tool exposure. A protocol
`notifications/tools/list_changed` event or an explicit
`engine.request_mcp_refresh(server_name)` marks a connected catalog for refresh at the
next pre-turn safe point. A complete new catalog is published for the next turn only;
the current turn keeps its original handlers and schema. A failed refresh retains the
last complete catalog, while cancellation propagates and leaves the refresh pending.

Interactive sessions use the same owner. `init_session()` only creates session state;
the first `await engine.astep(...)` starts MCP before capturing the turn, and later
`astep()` calls apply pending refreshes before their own turn snapshots. Keep every
step and `aclose()` on the event loop that started the transports. Synchronous
`engine.step(...)` rejects MCP-backed sessions because a temporary event loop cannot
own a persistent transport.

The stepwise API does not manage durable Run Journal or checkpoint commits. Use
`arun()`, `resume()`, and `fork()` when model and Tool transactions must survive a
process restart.

Engine dispatches MCP ToolCalls only from a complete model transaction. Known
incomplete, length-limited, failed, filtered, or cancelled terminals keep native or
text-salvaged calls as `invalid_tool_calls` diagnostics, but never execute them.

## Transport options

QitOS ships two transport implementations. For most local MCP servers that run as command-line processes, use `MCPServerStdio`:

```python
from qitos.mcp import MCPServerStdio

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)
await server.connect()
```

For remote MCP servers that expose an HTTP endpoint, use `MCPServerStreamableHttp`:

```python
from qitos.mcp import MCPServerStreamableHttp

server = MCPServerStreamableHttp(
    url="http://localhost:8080/mcp",
    headers={"Authorization": "Bearer token123"},
)
await server.connect()
```

Both transports perform the MCP initialization handshake automatically during `connect()`. After connecting, you can list available tools:

```python
tools = await server.list_tools()
for tool in tools:
    print(f"  {tool.name}: {tool.description}")
```

Both transports follow bounded `nextCursor` pagination rather than silently returning
only the first page. Each `MCPToolInfo` carries `name`, `description`, `input_schema`,
and typed MCP `annotations`. Annotation values are treated as untrusted hints:
missing `readOnlyHint` is not interpreted as read-only, and QitOS never infers
concurrency safety or retry permission from them.

Stdio uses newline-delimited JSON-RPC and accepts at most 8 MiB per frame by default.
An oversized frame is a typed MCP protocol error. Unexpected EOF and other fatal
reader failures become typed transport errors and trigger transport cleanup
automatically.

## Lower-level bridging

The `mcp_server_to_function_tools` function converts every tool on a connected MCP server into a `FunctionTool` instance. Use it when an application owns the connection and transport event loop itself; ordinary agents should use the Engine-owned path above.

```python
from qitos.mcp import MCPServerStdio, mcp_server_to_function_tools

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)
await server.connect()

tools = await mcp_server_to_function_tools(server)
```

Each returned `FunctionTool` wraps a remote MCP call. When the tool is executed, QitOS
sends a `tools/call` JSON-RPC request and projects the typed `MCPCallToolResult` into a
normal QitOS `ToolResult`. `structuredContent`, `_meta`, and content blocks remain
available; `isError=true` becomes `ToolResult(status="error")` rather than a successful
JSON value. JSON-RPC protocol failures, remote request errors, remote Tool errors,
timeouts, and cancellation remain distinguishable terminal outcomes.

The Streamable HTTP transport accepts JSON or SSE responses to POST, keeps the
negotiated session and protocol headers, and reconnects an idle GET stream with
`Last-Event-ID`. Only events from that GET notification stream advance the reconnect
cursor; IDs in POST responses do not. A session 404 has the stable
`MCP_SESSION_EXPIRED` classification. QitOS may reconnect and repeat safe catalog
discovery at the next turn boundary, but it never automatically replays a potentially
side-effecting `tools/call`.

You can add a name prefix to disambiguate tools when bridging multiple servers into the same registry:

```python
fs_tools = await mcp_server_to_function_tools(server, name_prefix="fs")
# Tool names become: fs__read_file, fs__write_file, etc.
```

Register the bridged tools in a `ToolRegistry` just like any other tool:

```python
from qitos import ToolRegistry

registry = ToolRegistry()
for tool in fs_tools:
    registry.register(tool)
```

## Filtering tools in an application-owned bridge

MCP servers often expose many tools, but your agent may only need a subset. `ToolFilter` controls which tools are bridged:

**Allow only specific tools:**

```python
from qitos.mcp import ToolFilter, mcp_server_to_function_tools

tool_filter = ToolFilter(allowed_tool_names={"read_file", "list_directory"})
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

**Block specific tools:**

```python
tool_filter = ToolFilter(blocked_tool_names={"delete_file", "move_file"})
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

**Custom filter function:**

```python
tool_filter = ToolFilter(filter_func=lambda name: name.startswith("read_"))
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

You can combine allowed and blocked lists. A tool name must be in the allowed list (if set) and not in the blocked list:

```python
tool_filter = ToolFilter(
    allowed_tool_names={"read_file", "write_file", "delete_file"},
    blocked_tool_names={"delete_file"},
)
# Only read_file and write_file pass
```

The evaluation order is:

1. If `filter_func` is set, its result is authoritative.
2. If `allowed_tool_names` is set, only names in the set pass.
3. If `blocked_tool_names` is set, names in the set are excluded.
4. Otherwise the name passes (no filtering).

## Application-owned async lifecycle

MCP server connections hold resources (subprocesses, HTTP clients) that must be cleaned up. Always pair `connect()` with `cleanup()`:

```python
from qitos.mcp import MCPServerStdio, mcp_server_to_function_tools, ToolFilter

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)

try:
    await server.connect()

    tools = await mcp_server_to_function_tools(
        server,
        tool_filter=ToolFilter(blocked_tool_names={"dangerous_op"}),
        name_prefix="fs",
    )

    # Use tools in your agent...
    for tool in tools:
        print(f"Bridged: {tool.spec.name}")

finally:
    await server.cleanup()
```

`MCPServerStdio.cleanup()` terminates and reaps its complete subprocess tree (first a
graceful group signal, then a forced tree kill after a 5-second timeout).
`MCPServerStreamableHttp.cleanup()` waits for an active POST, terminates the negotiated
session, and closes the HTTP client. Caller cancellation is propagated only after
those owned resources settle.

When a request is cancelled, both transports attempt the MCP cancellation notification
for a bounded period (250 ms by default). This notification is best effort: a blocked
or failed notification never delays local cancellation indefinitely, and cleanup does
not start a new notification while the transport is already closing.

The bridge, transport, and Engine all run on the caller's event loop. They do not
create a temporary or dedicated MCP event loop, so application code must not block
that loop while a bridged Tool is running.
