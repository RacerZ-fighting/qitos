The Model Context Protocol (MCP) is an open standard for connecting AI systems to external tools and data sources. QitOS can own an MCP server for one `Engine.arun()` lifecycle: it connects after preflight, discovers tools before the first model turn, executes calls on the transport's event loop, and removes the tools and closes the server when the run ends.

## Preferred: let Engine own the lifecycle

Pass explicit server instances to `AgentModule` and give the agent a `ToolRegistry`:

```python
from qitos import Engine, ToolRegistry
from qitos.mcp import MCPServerStdio

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/workspace"],
    name="filesystem",
)
agent = MyAgent(
    tool_registry=ToolRegistry(),
    mcp_servers=[server],
)

result = await Engine(agent).arun("Inspect the workspace")
```

The model sees provider-safe names such as `mcp__filesystem__read_file`; QitOS preserves the raw server and tool names for protocol calls. Names are sanitized, deduplicated, and bounded to 64 characters. Registrations are run-scoped, so the same registry can be reused by a later Engine run.

`mcp_servers=[]` is the normal default. It starts no MCP event loop, subprocess, or HTTP client. Configuration discovery, catalogs, and approval policy remain application concerns.

## Transport options

QitOS ships two transport implementations. For most local MCP servers that run as command-line processes, use `MCPServerStdio`:

```python
from qitos.mcp import MCPServerStdio

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)
await server.connect()
```

For remote MCP servers that expose an HTTP endpoint, use `MCPServerStreamableHttp`:

```python
from qitos.mcp import MCPServerStreamableHttp

server = MCPServerStreamableHttp(
    url="http://localhost:8080/mcp",
    headers={"Authorization": "Bearer token123"},
)
await server.connect()
```

Both transports perform the MCP initialization handshake automatically during `connect()`. After connecting, you can list available tools:

```python
tools = await server.list_tools()
for tool in tools:
    print(f"  {tool.name}: {tool.description}")
```

Each `MCPToolInfo` returned by `list_tools()` carries `name`, `description`, and `input_schema`.

## Lower-level bridging

The `mcp_server_to_function_tools` function converts every tool on a connected MCP server into a `FunctionTool` instance. Use it when an application owns the connection and transport event loop itself; ordinary agents should use the Engine-owned path above.

```python
from qitos.mcp import MCPServerStdio, mcp_server_to_function_tools

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)
await server.connect()

tools = await mcp_server_to_function_tools(server)
```

Each returned `FunctionTool` wraps a remote MCP call. When the tool is executed, QitOS sends a `tools/call` JSON-RPC request to the MCP server and returns the result.

You can add a name prefix to disambiguate tools when bridging multiple servers into the same registry:

```python
fs_tools = await mcp_server_to_function_tools(server, name_prefix="fs")
# Tool names become: fs__read_file, fs__write_file, etc.
```

Register the bridged tools in a `ToolRegistry` just like any other tool:

```python
from qitos import ToolRegistry

registry = ToolRegistry()
for tool in fs_tools:
    registry.register(tool)
```

## Filtering tools in an application-owned bridge

MCP servers often expose many tools, but your agent may only need a subset. `ToolFilter` controls which tools are bridged:

**Allow only specific tools:**

```python
from qitos.mcp import ToolFilter, mcp_server_to_function_tools

tool_filter = ToolFilter(allowed_tool_names={"read_file", "list_directory"})
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

**Block specific tools:**

```python
tool_filter = ToolFilter(blocked_tool_names={"delete_file", "move_file"})
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

**Custom filter function:**

```python
tool_filter = ToolFilter(filter_func=lambda name: name.startswith("read_"))
tools = await mcp_server_to_function_tools(server, tool_filter=tool_filter)
```

You can combine allowed and blocked lists. A tool name must be in the allowed list (if set) and not in the blocked list:

```python
tool_filter = ToolFilter(
    allowed_tool_names={"read_file", "write_file", "delete_file"},
    blocked_tool_names={"delete_file"},
)
# Only read_file and write_file pass
```

The evaluation order is:

1. If `filter_func` is set, its result is authoritative.
2. If `allowed_tool_names` is set, only names in the set pass.
3. If `blocked_tool_names` is set, names in the set are excluded.
4. Otherwise the name passes (no filtering).

## Application-owned async lifecycle

MCP server connections hold resources (subprocesses, HTTP clients) that must be cleaned up. Always pair `connect()` with `cleanup()`:

```python
from qitos.mcp import MCPServerStdio, mcp_server_to_function_tools, ToolFilter

server = MCPServerStdio(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
)

try:
    await server.connect()

    tools = await mcp_server_to_function_tools(
        server,
        tool_filter=ToolFilter(blocked_tool_names={"dangerous_op"}),
        name_prefix="fs",
    )

    # Use tools in your agent...
    for tool in tools:
        print(f"Bridged: {tool.spec.name}")

finally:
    await server.cleanup()
```

`MCPServerStdio.cleanup()` terminates the subprocess (first `SIGTERM`, then `SIGKILL` after a 5-second timeout). `MCPServerStreamableHttp.cleanup()` closes the HTTP client session.

The bridged functions submit calls back to the event loop where discovery occurred. Do not block that loop while executing a bridged tool. Engine-owned integration avoids this constraint by using one run-scoped MCP transport loop.
