# Checkpoint Resume and Journal Fork

QitOS checkpoints save an Agent state snapshot for resume after interruption. Session
journals persist complete model and Tool transactions and own executable Run branching.
Choose one persistence mode for an Engine; do not configure a checkpoint store and a
journal together.

This is essential for:
- **Long-running tasks** that may be interrupted (network errors, budget limits)
- **Branching experiments** that continue from a committed Journal boundary
- **Lineage inspection** across parent and Child Runs

## Step 1: Basic Checkpointing

Create a `CheckpointStore` and configure the Engine to use it:

```python
from qitos.checkpoint import InMemoryCheckpointStore, CheckpointConfig

# Create an in-memory store (use SqliteCheckpointStore for persistence)
store = InMemoryCheckpointStore()

# Pass it to the Engine
from qitos.engine import Engine
from my_agent import MyAgent

agent = MyAgent()
engine = Engine(agent, checkpoint_store=store, auto_approve=True)

# Run the agent — checkpoints are saved automatically
result = await engine.arun("Analyze the dataset")

# Access the latest checkpoint
config = CheckpointConfig(thread_id=result.run_id)
latest = await store.get_tuple(config)
print(f"Checkpoint at step {latest.checkpoint.step}")
```

`engine.last_checkpoint_id` is a read-only lifecycle value. It is `None` before the
first successful checkpoint commit, advances only after `CheckpointStore.put()`
succeeds, and is initialized to the source checkpoint during resume. Hooks can compare
this value across safe boundaries without accessing Engine private fields.

For persistent storage across sessions, use `SqliteCheckpointStore`:

```python
from qitos.checkpoint import SqliteCheckpointStore

store = SqliteCheckpointStore("./checkpoints.db")
```

## Step 2: Resuming a Run

If a run is interrupted, resume from the last checkpoint:

```python
from qitos.checkpoint import CheckpointConfig

# The thread_id identifies the run (usually the run_id)
config = CheckpointConfig(thread_id="my-run-001")

# Resume the run from its state and exact model-history snapshot
result = await engine.aresume_from_checkpoint(config)
```

The Engine restores the state from the latest checkpoint and continues execution from where it left off.

If the selected checkpoint is already terminal, the Engine returns its persisted state
without another model request, tool call, or checkpoint. When the resumed Engine has a
new `TraceWriter`, QitOS finalizes that empty trace with the persisted stop reason and
result.

## Step 3: Forking a Journal Run

Use a Journal-backed Run when the work must support executable branching. Fork only a
committed continuation position:

```python
from qitos import Engine
from qitos.kit.journal import JsonlRunCatalog, JsonlSessionJournal

journal_root = ".qitos/sessions"
run = await Engine(
    MyAgent(),
    journal=JsonlSessionJournal(journal_root),
    auto_approve=True,
).arun("Analyze the dataset")

catalog = JsonlRunCatalog(journal_root)
handle = await catalog.inspect_run(run.run_id)
boundary = handle.continuation_position
if boundary is None:
    raise RuntimeError("Run has no committed continuation boundary")

child_run_id = "my-run-001-branch-a"
child_journal = await Engine(
    MyAgent(),
    journal=JsonlSessionJournal(journal_root),
    auto_approve=True,
).afork_journal(
    handle.run_id,
    boundary,
    new_run_id=child_run_id,
)

# Resume the independent child without replaying committed Tools.
branch_result = await Engine(
    MyAgent(),
    journal=child_journal,
    auto_approve=True,
).aresume_from_journal(child_run_id)
```

The source Run is untouched. The Child owns an independent inherited prefix and can
resume even if the ancestor files later become unavailable.

## Step 4: Inspecting Run Lineage

Use the read-only catalog to resolve parents and direct children without opening a
writer lease or constructing an Engine:

```python
lineage = await catalog.lineage(child_run_id)
children = await catalog.children(handle.run_id)
print([item.run_id for item in lineage])
print([item.run_id for item in children])
```

Terminal Runs remain read-only under resume. Continue them by explicitly forking their
non-terminal `continuation_position` into a new Run id.

## Step 5: Durability Boundary

Before its first provider request, a fresh `Engine.arun()` awaits an `input`
checkpoint containing the initialized task, state, and history. Completed-step
checkpoints descend from that input boundary. Resuming the input checkpoint retries
step zero without writing a duplicate input checkpoint.

The Engine also awaits `CheckpointStore.put()` after each complete step. A step is not
considered durable until that write succeeds. SQLite work runs outside the event-loop
thread, and cancellation waits for an active database call to settle before
propagating. Store instances belong to one event loop. Memory and SQLite stores accept
the same JSON-serializable payloads.

## Step 6: Inspecting the Snapshot

Each checkpoint contains the state, original task, complete model-history prefix, and
snapshot parent needed by checkpoint resume:

```python
config = CheckpointConfig(thread_id="my-run-001")
tuple_ = await store.get_tuple(config)
print(tuple_.checkpoint.task_text)
print(tuple_.checkpoint.history.messages)
```
