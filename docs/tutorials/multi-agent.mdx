# Build Your First Multi-Agent System in QitOS

This tutorial walks through building a multi-agent code exploration system that
dispatches parallel child agents to investigate different parts of a codebase.

## What You'll Build

A coordinator agent that uses the child `Agent` tool to spawn multiple explorer
agents in parallel, each investigating a different directory. Results are
aggregated and synthesized by the coordinator.

## Prerequisites

- QitOS installed (`pip install qitos`)
- An OpenAI-compatible API key

## Step 1: Define the child's tools and prompt

A child is the same `Agent` implementation as its parent, constructed with
narrowed tools and budgets. Define what one explorer child may use:

```python
from qitos.core.tool_registry import ToolRegistry
from qitos.kit import CodingToolSet

EXPLORER_PROMPT = """\
You are a code explorer agent. Investigate directories and report findings.
Keep the final answer to a short factual summary.
"""

def explorer_tools(workspace_root: str) -> ToolRegistry:
    registry = ToolRegistry()
    registry.include(CodingToolSet(
        workspace_root=workspace_root,
        include_notebook=False,
        enable_lsp=False,
        enable_tasks=False,
        enable_web=False,
    ))
    return registry
```

## Step 2: Create the coordinator with the Agent tool

The coordinator registers the model-facing `Agent` tool. Its invocation factory
builds one fresh child per call with narrowed tools and budgets:

```python
from dataclasses import dataclass
from typing import Any
from qitos import Action, AgentModule, Decision, StateSchema, ToolRegistry
from qitos.core import TaskBudget
from qitos.kit import CodingToolSet, ReActTextParser
from qitos.kit.child import build_agent_child_invocation_factory
from qitos.kit.tool.agent import AgentTool

@dataclass
class CoordinatorState(StateSchema):
    pass

class CoordinatorAgent(AgentModule[CoordinatorState, dict[str, Any], Action]):
    def __init__(self, llm, workspace_root):
        registry = ToolRegistry()
        registry.include(CodingToolSet(workspace_root=workspace_root, ...))
        registry.register(
            AgentTool(
                invocation_factory=build_agent_child_invocation_factory(
                    model=llm,
                    tool_registry=explorer_tools(workspace_root),
                    system_prompt=EXPLORER_PROMPT,
                ),
                execution_mode="optional_background",
                child_budget=TaskBudget(max_steps=5),
            )
        )
        super().__init__(tool_registry=registry, llm=llm, model_parser=ReActTextParser())

    def init_state(self, task, **kwargs):
        return CoordinatorState(task=task, max_steps=12)

    def build_system_prompt(self, state):
        return (
            "You are a code analysis coordinator. Use the Agent tool once per "
            "independent directory investigation; same-response calls run "
            "concurrently. Synthesize their conclusions into your final answer."
        )

    def prepare(self, state):
        return f"Task: {state.task}"

    def reduce(self, state, observation, decision):
        if decision.mode == "final":
            state.final_result = str(decision.final_answer or "")
        return state
```

## Step 3: Run It

```python
coordinator = CoordinatorAgent(llm=llm, workspace_root="./my-project")
result = coordinator.run(
    task="Analyze this codebase. Investigate the auth, api, and db modules in parallel.",
    max_steps=12,
)
print(result.state.final_result)
```

The coordinator makes one `Agent` call per directory. With
`run_in_background=true` each call returns a parent-scoped child handle
immediately, and every completion arrives as a typed `agent.child.completed`
runtime event; foreground calls return the child conclusion directly.

## Keep coordination policy in the application

Manager/Worker, Planner/Executor, and review topologies are application policies, not
separate QitOS runtimes. Compose them from the general delegation primitives above, or
use the typed async `AgentTool` and `ChildControlToolSet` lifecycle when the application
needs durable handles, background Children, follow-up messages, waits, or interrupts.
This keeps nested Children on the same kernel while allowing every application to
narrow its own tools, context, budgets, and permissions.
