QitOS builds reproducible LLM agents on one minimal async agent loop: `Message ->
Model -> ToolCall -> ToolResult`, driven by the `Agent` façade. Whether you are
prototyping a new agent loop policy or shipping a production coding agent, QitOS
keeps your runs traceable, your tools explicit, and your results reproducible.

A long-running QitOS coding run stays readable — it does not degrade into opaque glue code.

![QitOS live coding run](/images/demo.gif)

## Two ways to author agents in QitOS

QitOS keeps two authoring paths intentionally.

### Façade-first

This is the default path: compose the runtime directly.

You choose:

- the model (any OpenAI-compatible, Anthropic, or local adapter)
- the system prompt
- the tool surface (a `ToolRegistry` of typed tools)
- turn and time budgets

```python
agent = Agent(model=model, tool_registry=registry, system_prompt="...", max_turns=10)
result = await agent.prompt("inspect the project")
```

Everything is explicit: no hidden planner, no second orchestrator.

### Preset-first

This is the fastest path when you want a stable baseline or quick model-family switching.

You start from:

- family presets (pre-configured adapter and request defaults for a model family)
- harness policies (resolved model-family metadata and context hints)
- preset tool builders (pre-assembled tool bundles for common workflows)

This path is especially useful when one agent should switch across Qwen, Kimi, MiniMax, `gpt-oss`, and Gemma 4 without rewriting the agent.

## Who QitOS is for

- **Researchers** — prototype new agent methods on a minimal, inspectable loop, then diff, replay, and publish the runs.
- **Agent builders** — build tool-using agents on a stable execution loop, instead of piling framework glue code on top of raw LLM calls.
- **Evaluators** — turn structured run artifacts into comparable, reviewable evidence with qita.

## Key capabilities

### Reproducible runs

Every QitOS run can persist an append-only JSONL journal: model transactions,
Tool started/terminal records, committed turns, and one terminal run record. The
journal is the canonical source for replay, recovery, and fork.

### Built-in observability with qita

`qita` is QitOS's trace-artifact viewer. Point it at a directory containing
compatible trace artifacts to inspect a run, replay its recorded timeline, and
export it to standalone HTML.

```bash
qita board --logdir runs
```

The board runs at `http://127.0.0.1:8765` and auto-refreshes as new runs appear.

<Note>
The minimal Agent loop does not yet attach `TraceWriter` automatically. Its canonical
JSONL journal is a separate persistence surface; automatic trace projection is tracked
in the Session/Harness migration.
</Note>

### Typed tools with strict admission

Tools declare strict input schemas and run through one admission/execution
pipeline: validation, permission, bounded concurrency, timeout, and exactly one
terminal `ToolResult` per call — including denied, timed-out, and cancelled
calls. Parallel batches commit results in input order.

### Subagents

Subagents run on the same `Agent` implementation as the parent with narrowed
tools and budgets. A Run-owned supervisor provides durable handles, background
execution, parent messages, waits, interrupts, and journal-backed recovery. Each
active Subagent keeps one shared step for a tool-free final answer; the Supervisor
delivers that model-authored text without synthesizing a replacement.

### MCP integration

Bridge Model Context Protocol (MCP) servers into QitOS tool registries. Connect to MCP servers via stdio or HTTP transport, filter which tools to expose, and manage async server lifecycles.

## Featured designs

### Single-loop architecture

QitOS is opinionated about one thing above all: there is one agent loop per run.

- the `Agent` façade owns the transcript, lifecycle events, and steering queues
- the loop owns turn mechanics: one immutable model/Tool snapshot per turn
- tools, memory, journals, and tracing attach to that loop instead of spawning separate orchestrators

### Preset-first model switching

QitOS gives you reusable authoring blocks instead of forcing every agent to rebuild the same wiring.

- preset tool bundles such as `coding_tools(...)`, `advanced_coding_tools(...)`, `web_tools()`, and `task_tools(...)`
- reusable memory adapters such as `WindowMemory`, `SummaryMemory`, `VectorMemory`, and `MarkdownFileMemory`
- family presets and harness policies for provider switching

### Trace-first observability with qita

QitOS assumes that if a run matters, it should be inspectable afterward.

Every traced run produces structured artifacts (saved files that record what happened during the run), and `qita` turns them into:

- a board for comparing runs
- replay for step-by-step inspection
- export for shareable standalone HTML

### Domain specialization without a new runtime

Domain agents are still ordinary QitOS agents — they do not need a separate runtime. Domain behavior is expressed through:

- prompt policy
- tool composition
- subagent decomposition

This makes specialization easier to reason about and easier to reproduce.

## Status

<Warning>
QitOS is currently **Beta**. Trace/qita behavior and canonical durable records remain supported during the runtime migration. Pin the installed version and follow the changelog rather than treating the public API as frozen.
</Warning>
